## 1. Introduction（前言）

隨著機器學習在各種情境越來越常被使用，很多時候我們拿到的資料其實不是「乾淨的答案」，而是混著雜訊的結果。那麼，在不知道真實函數長什麼樣子的情況下，我們要怎麼用模型把它逼近出來，並且不要被雜訊牽著走呢？

本次 Kaggle 作業提供的資料來自一個未知函數的輸出，其形式可寫成：

$$
y = f(x_1, x_2)
$$

其中訓練資料的 $y$ 被加入了雜訊（noise），因此模型不只要學到 $x_1, x_2$ 與 $y$ 的關係，也要盡量讓預測不要因為雜訊而偏掉。Kaggle 的評分方式採用 **Mean Squared Error (MSE)**，也就是預測值 $\hat{y}$ 與真實 $y$ 的平方誤差平均，分數越低越好。

## 2. Data Processing（資料處理）

這份資料的欄位其實很單純：`train.csv` 只有 `x1, x2, y`，`test.csv` 只有 `x1, x2`。一開始我還以為這題應該沒什麼資料處理的空間，但真的開始做之後才發現，這題的差別其實不在「清不清資料」，而是在「怎麼把輸入變成模型看得懂、也比較好學的形式」。如果只把 `x1, x2` 原封不動丟進去，模型常常會卡在某個分數上下，進步很有限。

所以我這邊大致做三件事：  
第一是把讀資料的流程固定好（避免 Kaggle 路徑或欄位對不上，一出錯就整個重跑）。  
第二是做特徵工程（Feature Engineering），把一些可能跟函數形狀有關的資訊補進去。  
第三是做標準化（Standardization），讓後面的 Ridge 或神經網路訓練起來比較穩定。

在特徵工程方面，我最後整理成兩套特徵（v1 / v2）。主要原因是我不太敢只押一種表達方式，因為這題的函數是未知的：它可能長得像多項式，也可能有週期性，甚至可能跟「距離中心多遠」這種資訊有關。所以我把半徑寫成：

$$
r = \sqrt{x_1^2 + x_2^2}
$$

然後把「多項式／週期（$\sin$、$\cos$）／指數（$\exp$）／極座標相關」這幾種常見的方向都放進去，讓不同模型可以各自吃到自己比較擅長的訊號。v1 和 v2 的差別，主要是一些特徵組合與範圍的調整（例如多項式階數、週期特徵的組合方式等），我會用交叉驗證結果去看哪一套比較穩。

這部分我一開始其實是參考網路上的做法跟一些回歸/函數逼近常見的特徵設計方向，再去找相關文章或筆記確認思路，然後用 NotebookLM 幫我把重點整理出來（例如哪些特徵比較常被用來描述週期、哪些適合描述距離），最後再自己改成適合這題的版本。當我不確定某個特徵加下去到底會不會造成問題時，我也會用 GPT 幫我檢查「這樣做會不會資料洩漏 / 會不會讓尺度爆掉 / 可能會不會不穩」，但真正要不要留，還是以我自己跑出來的 CV / OOF 結果為準。

最後是標準化，我用 `StandardScaler` 把特徵做 scaling。原因很直覺：因為特徵裡面同時有多項式、$\sin/\cos$、$\exp$、極座標等，尺度差異會非常大，如果不標準化，模型可能會被某些數值很大的特徵牽著走，導致訓練不穩、或是收斂很慢。把尺度統一之後，不管是 Ridge 的權重學習，還是 NN 的訓練，都會比較穩定。

## 3. Model Architecture（模型架構）

這題在「未知函數 + label 有雜訊」的情況下，我自己做下來的感覺是：只靠單一模型很容易會有盲點。有時候模型看起來擬合得很像，但其實是把噪聲也一起學進去；有時候模型很穩，但又不夠貼近函數的彎曲程度。所以我最後採用的方向是「多模型集成（Ensemble）」：用不同型態的模型互相補強，再用融合把它們的優點留下來。

整體架構我分成三個部分：

1) **Feature-based Ridge（線性模型 + 強特徵）**  
   我用 v1 / v2 兩套特徵各自訓練一個 Ridge。因為特徵本身已經把很多非線性的形狀轉成「線性可學」的形式，所以 Ridge 其實可以當成一個非常穩的 baseline，而且對雜訊也比較不容易亂飄。

2) **Neural Network（Residual MLP）**  
   我用 PyTorch 訓練多個 MLP（base / wide / deep），再搭配多個 seed。這邊的目的不是要做一個超大的網路，而是用不同設定讓結果更穩，避免某一次訓練剛好學歪。

3) **Stacking / Blending（融合）**  
   我把 Ridge(v1)、Ridge(v2)、NN 的預測當成 meta features，再做一層線性 stacking（或 blending），用 OOF 的表現去決定最後的混合方式。

![image](https://hackmd.io/_uploads/HJYs5ra4Wl.png)

在 NN 的設計上，我用的是 Residual MLP。加 residual 的原因其實很單純：我希望訓練的時候比較不容易崩掉，讓網路比較像是在「逐步修正」而不是整個重學一次。另外我也加了 BatchNorm、Dropout 這些比較常見的穩定化手段，避免模型在 noisy label 下太容易過擬合。

Loss 的部分，雖然 Kaggle 評分用的是 MSE，但我訓練時用的是混合 loss（MSE + SmoothL1）。我的理解是：MSE 讓訓練方向跟評分方式一致，但遇到比較極端的點時，MSE 會放大影響；SmoothL1 對這種點相對沒那麼敏感，所以混在一起可以讓訓練比較穩一點。至於版本比較跟最後選擇，我仍然用 raw MSE 跟 OOF 表現去判斷，確保我的指標跟 Kaggle 的分數是對齊的。

另外這一段（Residual、BN/Dropout、多 seed、stacking）我一開始也不是自己就直接想完整套出來，而是先看一些常見的 Kaggle regression ensemble 做法，找幾篇文章/筆記對照「為什麼要多 seed」、「為什麼 stacking 會有效」，再用 NotebookLM 幫我整理出幾個我覺得最有用、也最適合這題的部分，最後再把它們放進我的程式裡跑。中間也有用 GPT 幫我檢查架構/流程有沒有明顯 bug（例如 OOF 的流程是不是寫錯、融合是不是有資料洩漏），但同樣地，最後要不要用、怎麼調，還是我自己看 OOF / Public LB 的結果來決定。

## 6. Difficulties Encountered（遇到的困難）

這次作業我遇到最多的困難，其實不是某一行程式寫不出來，而是「不知道該往哪個方向改」。第一個困難是一開始我只會一直改模型層數、改 learning rate，但分數不一定會有所變動，有時甚至還會更差。後來我才慢慢發現：要先有一個合理的猜測，例如「函數可能有週期性」、「可能跟半徑有關」，才知道自己下一步要試的是特徵、驗證方式，還是模型本身。

第二個困難是我第一次把 Kaggle 的流程做得比較完整，從讀資料、訓練、CV、到輸出 `submission.csv`，每一個環節都有可能出錯。尤其是 `id` 是否正確、submission 格式是不是對的，這些看起來很小，但一錯就會卡很久，我也確實因為這個問題卡了一整天，最後才用防呆方式（例如 `safe_submission_id()`）把這個問題解決。

第三個困難是訓練時間和除錯成本。像 v9 這種多 seed、多 fold、又多模型的 ensemble，一跑就很久，有時要等 20 幾分鐘，甚至 30 幾分鐘，只要哪裡設定不小心寫錯，就要整個重來。而且我每次都得等結果跑完，才知道這一版到底有沒有進步，才能決定下一步要改什麼，所以一天能試的次數其實很有限，也會覺得等待真的很折磨。後來我就改成先用小規模測試，像是縮短 epochs、減少 fold/seed，接著確認流程沒問題之後，再開完整設定跑最終的版本。

第四個困難是很多技巧不是課堂上直接教到的，例如 stacking、TTA、或者一些特徵設計方向。一開始我會覺得「這些我怎麼可能自己想到」，所以我採取的方式是：先去網路看文章和影片，搭配 NotebookLM 幫我整理文獻重點，理解大概原理後，再請 GPT 幫我看程式、幫我除錯、也幫我指出哪些地方可能能改善。我也常把 submission.csv 丟給 GPT 問它「從分數看起來像什麼問題、可以往哪裡改」。雖然不是全都照做，但這個過程讓我少走很多彎路，也幫我省下超級多時間成本。
